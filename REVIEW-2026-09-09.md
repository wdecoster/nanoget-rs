## Fixed

### 1. FASTQ quality scores were never Phred-decoded — every value off by +33 ✅

`bio::io::fastq::Record::qual()` returns the **raw ASCII quality line**, not decoded
Phred scores. `average_quality` treated it as Phred, so results were `true_Q + 33`,
then clamped to 60 — meaning everything above ~Q27 collapsed to a flat 60.

Fixed by adding `utils::average_quality_phred33` and using it in
`process_fastq_from_reader`. `~/repos/nanotest/reads.fastq.gz` now reports
`count=371 mean=10.09 median=10.29 min=7.02 max=13.29`, byte-identical to python
nanoget on the same file (it previously reported a mean of ~43).

Regression tests: `utils::tests::test_average_quality_phred33_*` and
`tests/integration_tests.rs::test_fastq_quality_{is_phred33_decoded,averages_in_probability_domain}`.

### 2. uBAM piped on stdin produced zero reads, silently, with exit status 0 ✅

`sniff_stdin_bytes` classifies any BGZF stream as `Bam` — it cannot read the header
without consuming the stream — so unaligned BAM went to `process_bam`, whose
`is_unmapped()` filter discards every record in a uBAM. `--file-type ubam` did not help
because `-t` is ignored for stdin (finding 13, still open). Compounding it,
`extract_metrics_stdin` returned without the zero-read guard the file path has.

Fixed by splitting `extract_ubam_records` out of `process_ubam` and adding
`extract::process_stdin_alignments`, which opens stdin once and dispatches on
`header().target_count()`, the same test `sniff_bam_or_ubam` already uses for files. The
CRAM required-field set now includes `SAM_QUAL` on the unaligned branch, which reads
qualities. The zero-read guard was added to the stdin path.

Regression tests: `tests/stdin_tests.rs` (also puts the previously-unused `assert_cmd`
dev-dependency to work).

### 3. Reachable panic: integer underflow on an empty collection ✅

`src/metrics.rs:204` — `(percentile / 100.0 * (lengths.len() - 1) as f64)`

`MetricsCollection::reads_above_length_percentile` on a collection with no reads
underflows `usize`. Confirmed:

```text
thread 'probe_percentile_empty' panicked at src/metrics.rs:204:43:
attempt to subtract with overflow
```

Release masked it via the `.get(index).unwrap_or(0)` on the next line, so it was a
debug-only panic — but it is a `pub fn` reachable from library code with no documented
precondition. `calculate_percentile` (`src/metrics.rs:487`) does the same arithmetic and
guards it at `:488`; this one did not.

Fixed by returning an empty collection for empty input and clamping the percentile, so
an out-of-range or NaN argument saturates at the ends of the distribution instead of
indexing past it.

This was the only unguarded index arithmetic in the crate. There are no
`unwrap()`/`expect()`/`panic!`/slicing hazards anywhere else in `src/`.

Regression tests: `metrics::tests::test_reads_above_length_percentile_{on_empty_collection,thresholds}`.

### 4 & 5. `FileType::sniff` guessed compressed files from their extension ✅

`src/formats.rs:64-78` (fell back to extension) and `src/formats.rs:130-139` (the
compressed arm returned only `Fastq`/`Fasta`/`Bam`)

Two symptoms of one cause: `sniff` never looked inside a compressed file. Gzipped rich
FASTQ was reported as plain `Fastq`, losing channel / start time / run ID for the most
common on-disk form — confirmed with one identical read three ways:

| input | `sniff` result |
| --- | --- |
| `rich.fastq` | `FastqRich` |
| `rich.fastq.gz` | **`Fastq`** |
| same bytes via `sniff_stdin_bytes` | `FastqRich` |

And bzip2 files were rejected outright (`BZh` magic matches none of the checked cases,
and the fall-through never consulted `from_extension`), as were gzipped summary files
(the compressed arm omitted the `txt|tsv`→`Summary` case the uncompressed arm had):

```text
rich.fastq.bz2            -> Err(ParseError("Cannot determine file format for: ..."))
sequencing_summary.txt.gz -> Err(ParseError("Cannot determine format for gzipped file: ..."))
```

Both are formats the extractor itself handles fine — `utils::open_file` decompresses
`.bz2` and `.gz` — so they were usable from the CLI with an explicit `-t` but unusable
from nanoplotrs, which picks its `FileType` from `sniff` (`nanoplotrs/src/lib.rs:58`).

Fixed by making `sniff` read content rather than guess:

- extracted `classify_text_head`, which decides FASTQ (plain or rich) / FASTA / summary
  from a head of bytes, and routed **both** `sniff` and `sniff_stdin_bytes` through it,
  so the same bytes now classify the same way however they arrive;
- `sniff` decompresses the head of gzip *and* bzip2 streams (`read_head`) and classifies
  that, falling back to `from_extension` only when the content is unrecognisable — so a
  truncated or corrupt but conventionally named file still resolves;
- `from_extension` gained the `txt|tsv`→`Summary` case in its compressed arm, factored
  into `summary_by_name` so both arms share it;
- the head probe grew from 512/1024 bytes to a single `HEAD_BYTES = 8192`, enough for
  the ~38-column header of a barcoded summary, and the summary header is now compared
  lossily so a head truncated mid-character still classifies.

Note the deliberate precedence change: content now wins over extension for compressed
files, so a `.fasta.gz` that actually contains FASTQ is reported as `Fastq`.

Results, all previously wrong or errors:

| input | before | after |
| --- | --- | --- |
| `rich.fastq.gz` | `Fastq` | `FastqRich` |
| `rich.fastq.bz2` | `Err` | `FastqRich` |
| `sequencing_summary.txt.gz` | `Err` | `Summary` |
| `nanotest/reads.fastq.gz` | `Fastq` | `FastqRich` |

That last one is the real-world case: extracting it as `FastqRich` now yields channel,
start time and run ID where before it produced none.

Regression tests: `tests/sniff_tests.rs` (5 tests, covering plain/gzip/bzip2/stdin
agreement, the extension fallback, wide summary headers, and the rejection cases).

### 8. Zero-length reads were kept; python drops them ✅

`src/extract.rs:435-468` (summary), `src/extract.rs:176` (FASTA)

Python's `process_summary` ends with `datadf.loc[datadf["lengths"] != 0]` and documents
it ("Only reads which have a >0 length are returned",
`nanoget/extraction_functions.py:15`). The Rust parser has no such filter. Confirmed — a
summary row with `sequence_length_template=0` is emitted with length 0 and quality 0.0,
dragging `min` to 0 and skewing N50 and the mean. Confirmed for FASTA too: a `>s1` with
an empty sequence yields a length-0 read.

Same idea for FASTQ, where python's `.dropna()` (`extraction_functions.py:447`) removes
reads whose `ave_qual` came back `None`.

Fixed across every parser — FASTQ, FASTA, BAM, uBAM and summary — so a read with no
bases never reaches the statistics. The count of dropped reads is logged at `info` level
(`log_skipped_empty`) so a shrinking read count is traceable rather than mysterious.

Verified unchanged on real input: `nanotest/reads.fastq.gz` 371 reads,
`nanotest/alignment.bam` 1115, `nanotest/sequencing_summary.txt` 371. A summary row with
`sequence_length_template=0` is now dropped, taking its channel out of the distribution
with it, and the length minimum rises from 0 to the true minimum.

Regression tests: `tests/malformed_tests.rs::test_zero_length_reads_are_dropped_from_{fasta,summary}`
and `test_all_zero_length_is_an_error`.

### 11. Malformed FASTQ records were accepted silently ✅

`src/extract.rs:112-116`

`bio` provides `Record::check()` (`bio-3.0.0/src/io/fastq.rs:378`), validating non-empty
id, ASCII, and equal sequence/quality length. It is never called. Confirmed: a record
with a 4-base sequence and a 2-character quality line is accepted, reported as length 4,
with a quality averaged over only 2 bases.

Truncated records at EOF *are* caught — bio errors with "Incomplete record" (confirmed).
This is specifically the interior-corruption case.

Fixed with `check_fastq_record`, which rejects a sequence/quality length mismatch or a
missing read id as a `ParseError` naming the record number, the read id and both
lengths — corrupt input from new users is common enough that a silent wrong answer is
worse than a hard stop. Applied to `fastq`, `fastq-rich` and `fastq-minimal` alike, so no
mode accepts what another rejects.

Only O(1) checks are made. `bio`'s own `Record::check()` also scans every base for
non-ASCII; that is a second pass over the read (finding 18 territory) for a corruption
that a length mismatch almost always catches anyway, so it is deliberately skipped.

This immediately caught two genuinely malformed test fixtures — `create_test_fastq` in
both `tests/integration_tests.rs` and `tests/library_api_tests.rs` wrote a 99-base
sequence against a 100-character quality line, and the assertions had baked that in.
Both fixtures were corrected.

Regression tests: `tests/malformed_tests.rs::test_mismatched_quality_line_is_an_error`,
`test_error_names_the_offending_record`, and `test_valid_fastq_is_not_rejected` (which
pins CRLF, header descriptions and a missing trailing newline as *valid*).

### 9. Summary parser: optional metadata columns ✅ (9a, 9b fixed; 9c documented)

`src/extract.rs:435-454`

**No test data needed** — all three are reproducible from synthetic summary files, and
the two real summary files on disk (`nanotest/` and `nanocomp/nanotest/`) were checked
and agree: `start_time='3733.02575'`, `duration='22.56375'`, `channel='124'`, i.e. plain
floats and integers. Splitting this into the three things it actually is, with a concrete
proposal for each:

**9a — Silent failure conflates "column absent" with "column present but garbage".**
`length` and `quality` are hard errors on a missing column or unparseable value (`:437`,
`:443`), aborting the whole run. `channel`, `start_time` and `duration` use
`row.get(..).and_then(|s| s.parse().ok())` (`:447`, `:451`, `:454`) and vanish silently
either way. A summary file with a `channel` column full of something unexpected loses all
channel data with no diagnostic, and the user sees a NanoPlot run with no channel plots
and no reason given.

*Proposal:* keep absence silent — not every summary file has every column, and that is
normal — but make a **present but unparseable** value a `ParseError` naming the column
and the offending value. Mechanically, replace `and_then(|s| s.parse().ok())` with a
match that distinguishes `None` from `Some(unparseable)`. This is the same principle as
finding 11: a file that is not what it claims to be should say so rather than quietly
producing less. Worth deciding whether an empty string (`""`) counts as absent — real
summary files do leave optional cells blank, so it probably should.

**9b — `start_time` accepts only float seconds; the rich-FASTQ path accepts more.**
`:451` uses `parse::<f64>().and_then(parse_timestamp)`, while `parse_start_time`
(`src/extract.rs:619`) already handles RFC3339 *or* float seconds and is used for rich
FASTQ. A summary file with ISO timestamps would yield `None` for every read, silently.

*Proposal:* call `parse_start_time` in the summary parser too. One line, strictly more
accepting, and it removes an inconsistency between two paths that should agree.

*Caveat, and the reason this is low priority:* this is **speculative hardening, not a
known bug**. Both summary files on disk use float seconds, and python nanoget only ever
reads the column as a float. No file with an ISO `start_time` has been observed. If you
know of a basecaller that emits one, that would promote this; otherwise it is cheap
insurance.

**9c — `start_time` is interpreted as a Unix epoch, producing dates in 1970.**
`parse_timestamp` (`src/extract.rs:21`) feeds the value to `Utc.timestamp_opt`, so
`3733.02575` becomes `1970-01-01T01:02:13Z` (confirmed). ONT writes seconds since the
*start of the run*, not since the epoch.

*Proposal: leave it, and document it.* There is no correct absolute timestamp to compute
— the run start is not in the file — and python nanoget does exactly the same thing
(`nanoget/nanoget.py:150` reads the column as `datetime64[s]`, i.e. epoch seconds, then
subtracts the minimum). So the behaviour is already at parity, and every consumer that
matters uses the value relatively. The only real defect is that the public JSON exposes
an absolute-looking `start_time` that is meaningless in isolation, which is a
documentation problem, not a code one. Changing the encoding would break parity with
python for no gain.

**Implemented as proposed.** 9a: `optional_column` distinguishes absent (and blank —
real summary files leave optional cells empty) from present-but-unparseable, the latter
being a `ParseError` naming the column and value. 9b: the summary parser now calls
`parse_start_time`, so it accepts RFC3339 as well as seconds. 9c: left alone, with the
epoch-seconds interpretation and its python parity noted in a comment at the call site.

Regression tests: `tests/malformed_tests.rs::test_unparseable_summary_column_is_an_error`,
`test_blank_summary_cells_are_treated_as_absent`, `test_summary_accepts_rfc3339_start_time`.

### 13. `--file-type` was required, and silently ignored for stdin ✅

`src/extract.rs:37-38` and `:496`

`-t` is `required = true` (`src/cli.rs:26`) yet the stdin branch is taken before
`args.file_type` is read, and re-sniffs from the peeked bytes. Confirmed:
`cat q.fastq | nanoget extract -t fasta -f tsv -` happily parses FASTQ. There is
consequently no way to force `fastq-rich` on a stream whose first read lacks metadata,
and no way to force `fastq-minimal`.

(The `ubam` case this used to break was already handled by the finding-2 fix, which
dispatches on the SAM header — so an explicit `-t bam` on a uBAM stream still does the
right thing.)

**Resolved by making `-t` optional rather than by honouring it.** Since findings 4 and 5,
`sniff` classifies every `FileType` except `FastqMinimal` — which is a processing mode
(lengths only) rather than a format, and so is not detectable in principle. That makes
`-t` redundant for detection, which is what it was mostly being used for.

`ExtractArgs::file_type` is now `Option<FileType>`. When `None`, each file is classified
from its own content, so a mixed set works in one run; when `Some`, it overrides
detection everywhere, stdin included, which is now the documented way to reach
`fastq-minimal` on a stream. The inconsistency is gone because there is no longer a
required argument being ignored.

Confirmed: `nanoget extract reads.fastq.gz alignments.bam sequencing_summary.txt` detects
`FastqRich`, `Bam` and `Summary` respectively and reports 1857 reads, exactly the sum of
the three run separately (371 + 1115 + 371).

Regression test: `tests/cli_tests.rs::test_file_type_is_optional_and_detected_per_file`.

### 15. Rich FASTQ with missing metadata degraded silently ✅

`src/extract.rs:126-134`

When `parse_rich_fastq_metadata` returns `None` the read is kept with no channel, time
or run ID, and nothing is logged. Confirmed on a mixed file: read 1 gets `ch=42` and a
timestamp, read 2 gets blanks. Python exits with a diagnostic naming the offending
header (`nanoget/extraction_functions.py:544-549`). Aborting is probably too harsh, but a
counted warning at end of file would tell the user why their time plots are empty.

Fixed as an error, matching the reasoning behind finding 11: a record in a rich FASTQ

**stricter**: it requires `ch`, `start_time` *and* `runid` on every record and exits if

Regression test: `tests/malformed_tests.rs::test_rich_fastq_without_metadata_is_an_error`

### 16. Non-finite statistics serialised to `null` and broke the type's own `Deserialize` ✅

`src/metrics.rs:459`, `:462`

`sort_by(...unwrap_or(Equal))` handles NaN "gracefully" only in the sense of not
panicking; the resulting min/median/max are arbitrary and `mean` becomes NaN.
serde_json then writes `null`. Confirmed:

```json
"quality_stats":{"count":1,"mean":null,"median":null,"min":null,...}
```

`StatsSummary.mean` is `f64`, not `Option<f64>`, so this JSON cannot be read back through
the `Deserialize` impl derived at `src/metrics.rs:429`. NaN is reachable from real input:
`src/extract.rs:441-445` parses the quality column with `f64::from_str`, which accepts
`nan` and `inf`.

Fixed in two layers, because the sources and the guarantee are different problems.

**At the boundaries**, a non-finite number is treated as *not measured* rather than as
corruption — `nan` in a quality column means a read that failed QC, not a broken file, so
aborting the run would reject perfectly good input. `optional_column` now returns `None`
for any cell that parses as a non-finite number, the same as for a blank cell; the
required quality column is recorded as an absent quality; `parse_timestamp` rejects
non-finite explicitly (NaN fails every comparison, so `NaN as i64` was saturating to 0 and
silently becoming the Unix epoch); and `get_de_tag` filters a non-finite minimap2
divergence.

**At the summary**, `MetricsSummary::from_reads` filters non-finite values alongside
absent ones. This is what makes the round-trip an actual guarantee: `ReadMetrics` has
`pub` fields, so a library caller can set a NaN directly without going near a parser.
`StatsSummary` now documents that every field is finite.

Note the asymmetry that follows: a per-read `quality` of NaN still serialises as `null`,
but that field is `Option<f64>` and reads back as `None`, so the round-trip holds.

Regression tests: `metrics::tests::test_json_output_round_trips`,
`test_non_finite_values_are_excluded_from_summaries`,
`test_summary_is_absent_when_every_value_is_non_finite`, and
`tests/malformed_tests.rs::test_nan_summary_{quality_is_treated_as_absent,start_time_is_absent_not_epoch}`.

## Closed by decision

### 7. Percent identity differs from python nanoget (~3.6 points) — documented ✅

`src/extract.rs:258-265`

Rust computes gap-compressed identity: `1 - (NM - gap_bases + gap_count) / (matches + gap_count)`.
Python computes BLAST-style identity: `1 - NM / (match + ins + del)`
(`nanoget/extraction_functions.py:373-376`).

Measured on `~/repos/nanotest/alignment.bam`, same 1115 reads:

| | mean | median | min | max |
| --- | --- | --- | --- | --- |
| nanoget-rs | 89.96 | 90.84 | 73.84 | 95.12 |
| nanoget (python) | 86.35 | 87.89 | 49.09 | 93.81 |

The minimum differs by 25 points.

**Closed by decision, 2026-09-09:** the gap-compressed formula is intentional. It counts
each indel once regardless of length, which is the more meaningful measure for nanopore
reads whose errors are dominated by homopolymer indels, and it is the definition behind
the minimap2 `de` tag the code already prefers when present (`src/extract.rs:203-211`) —
so the two sources agree rather than mixing conventions. Nothing to fix; the problem was
that it was undocumented.

Documented in three places a reader would actually look: the `alignment_stats` doc
comment, the `ReadMetrics::percent_identity` field doc, and a new "Known differences in
output" section in the README, which also records the two related divergences below.

Related smaller divergences, now documented in the same README section:
`src/extract.rs:342-346` maps MAPQ 255 to `None` where python keeps the literal 255, and
BAM/CRAM report no `quality` at all (finding 6).


### 6. BAM/CRAM never produce read quality or aligned quality

**Closed by decision, 2026-09-09:** for aligned data the percent identity that BAM/CRAM
*does* provide is the superior measure, so the absent Phred quality is not a gap worth
closing. Recorded here because the divergence from python nanoget is real and will come
up again.

`src/extract.rs:341-353`

`extract_bam_records` computes length, aligned length, MAPQ and percent identity, then
passes `None` for `aligned_quality` at `:350`, and never touches `record.qual()`.
Confirmed — `quality` and `aligned_quality` are empty for all 1115 reads of
`~/repos/nanotest/alignment.bam`.

Python nanoget returns both: `ave_qual(read.query_qualities)` and
`ave_qual(read.query_alignment_qualities)`
(`nanoget/extraction_functions.py:338-339`). So for BAM input nanoplotrs loses the
quality histogram, the length-vs-quality plot and the quality-vs-identity plot that
python NanoPlot draws.

**Trap if this is ever revisited:** `src/extract.rs:299-304` requests
`CRAM_OPT_REQUIRED_FIELDS` *without* `SAM_QUAL`, telling htslib to skip decompressing
the quality stream for CRAM. Reading `record.qual()` after that yields a synthetic
all-`0xff` array rather than an error. The stdin path added for finding 2 handles this
by adding `SAM_QUAL` on the branch that needs it; the by-path route does not.

### 10. Summary parser has no `alias` fallback for barcodes — deferred

`src/extract.rs:456-460`

Only `barcode_arrangement` is read. Python falls back to the `alias` column when
`barcode_arrangement` is absent and reconciles the two when both are present
(`nanoget/extraction_functions.py:83-89`, `:125-155`) — logic that exists specifically to
work around a dorado bug. Rust's `--barcoded` on such a file yields no barcodes and no
error.

**Deferred, 2026-09-09:** nanoplotrs is not in use yet, so there is no one to hit this.
The `alias`-only summary files exist, but adding the fallback and the reconciliation
logic around it is complexity bought against a hypothetical report. Revisit if a user
turns up with such a file and `--barcoded`.

## Per-read hot-path allocations

Measured on a release build, 2M × 300 bp reads (1.36 GB FASTQ), before and after the
Tier 1 work below.

| mode | wall before → after | peak RSS before → after |
| --- | --- | --- |
| `fastq-minimal`, TSV | 1.45 → **1.08 s** | 755 → **411 MB** |
| `fastq-minimal`, JSON | 2.01 → **1.40 s** | 1066 → **412 MB** |
| `fastq`, TSV | 2.10 → **1.58 s** | 834 → **491 MB** |
| `fastq`, JSON | 2.29 → **1.88 s** | 1182 → **490 MB** |
| `fastq-rich`, TSV | 2.89 → **2.01 s** | 898 → **554 MB** |
| `fastq-rich`, JSON | 2.94 → **2.69 s** | 1311 → **554 MB** |

Peak memory is now **independent of output format** — the point of streaming — and down
by 38–61%. `size_of::<ReadMetrics>()` is 192 bytes, so of the 554 MB that remains for
`fastq-rich`, 384 MB is the records themselves, ~80 MB the per-read `read_id` strings and
~63 MB the per-read `run_id` strings (finding 21).

### Tier 1 — done ✅

- **24 (stream the output).** `MetricsCollection::write_tsv<W: Write>` writes a row at a
  time; `to_tsv` is retained as a wrapper over it. `main.rs` streams into a `BufWriter`
  over the file or locked stdout, and JSON goes through `serde_json::to_writer_pretty`.
  Per-cell `format!` temporaries are gone too: `OptFixed`/`OptDisplay`/`OptRfc3339` are
  `Display` adapters that render an `Option` straight into the output. This is where
  nearly all of the memory reduction came from.
- **25 (`with_capacity`).** `combine` reserves the exact total, and takes the single
  dataset as-is in the common one-file case rather than copying every read. Parser
  accumulators start at `INITIAL_READ_CAPACITY`; a read count genuinely cannot be
  estimated from file size (record length varies from ~100 bases to ~100 kb), so this
  only skips the cheap early doublings — the expensive ones are avoided in `combine`.
- **22 (stop discarding per-file summaries).** `process_single_file` returns
  `Vec<ReadMetrics>`, and `MetricsCollection::combine` now takes `Vec<Vec<ReadMetrics>>`
  so the summary is computed exactly once. Taking the reads rather than whole collections
  makes the waste structurally impossible rather than merely avoided.

Output is unchanged apart from one cosmetic difference: TSV no longer ends with a blank
line, which `println!` used to add after content that already ended in a newline.

### Tier 2 — measured, and mostly not worth it

Each item benchmarked in isolation, then put in the context of a real run:

| item | measured | in context |
| --- | --- | --- |
| **20** summary `HashMap` per row ✅ | 0.32 s per 1M rows (99% of field-access cost) | **35% of summary-file runtime** — done; 4.84 s → 3.16 s on 4M rows |
| **23** statistics double copy | 0.030 s per metric (54%) | ~4–8% of a FASTQ run, over 2–4 metrics; frees ~16 MB per metric transiently |
| **19** `raw_cigar()` | 0.4 µs per alignment (17% of CIGAR access) | **0.4% of a BAM extraction pass** — BGZF decompression dominates entirely |

**Outcome: 20 is done** and beat its estimate. 19 is dropped — listing it in Tier 2 was a
mistake on my part, the `Vec` per record being real but invisible next to decompression.
23 remains available at ~4–8% of a FASTQ run, the only allocation item left with any
measurable value.

The honest summary is that **Tier 2 has little left to give except for summary input**.
For FASTQ and BAM the remaining headroom is ~5%; for summary files it is ~27%, all of it
in finding 20. And no Tier 2 item touches memory: after Tier 1 the peak is dominated by
`ReadMetrics` itself (768 MB of the 865 MB a 4M-row summary uses), which is finding 21 and
the closing design question, not an allocation to shave.

### 18. Four `String` allocations per read from `bio`'s `records()` iterator

`src/extract.rs:111`, `:154`, `:174`

`Records::next` calls `Record::new()` on every iteration
(`bio-3.0.0/src/io/fastq.rs:502`), allocating fresh `id`, `desc`, `seq` and `qual`
`String`s — `seq`/`qual` grow to full read length, so a 20 kb ONT read means two 20 KB
heap allocations per record, immediately discarded. `bio` exposes
`Reader::read(&mut record)` (`fastq.rs:246`, and the fasta equivalent) precisely so one
`Record` can be reused across the loop. Largest avoidable cost in the FASTQ path.

### 19. A `Vec` allocation per record for the CIGAR — measured, not worth doing

`src/extract.rs:222`, `:239`

`record.cigar()` decodes into an owned `CigarStringView` (a `Vec<Cigar>`) on every call.
`alignment_stats` only sums op lengths, which `record.raw_cigar() -> &[u32]` provides
with no allocation. One `Vec` per alignment, discarded immediately.

### 20. A `HashMap` per row in the summary parser ✅

`src/extract.rs:421` — `let row: HashMap<&str, &str> = headers.iter().zip(record.iter()).collect();`

Every summary row allocated a hash map, hashed and inserted every column, then did 6
string-keyed lookups, for a column→index mapping fixed by the header.

Fixed with `SummaryColumns::resolve`, which resolves every position once from the header
row; each row is then a handful of slice indexes. Measured on a 4M-row summary file:
**4.84 s → 3.16 s, a 35% cut** — more than the 27% predicted.

It also improves an error: a missing required column is now detected at the header, so a
file with the wrong columns fails immediately instead of on its first data row.

Regression coverage: the existing summary tests, plus the real
`nanotest/sequencing_summary.txt` verified unchanged (371 reads, identical statistics).

### 21. Per-read `String`s for values that are constant across the file ✅

`src/extract.rs:132` (`run_id`), `src/extract.rs:457` (`barcode`),
`src/metrics.rs:136` (`dataset`)

A run ID is one 36-char UUID repeated across every read; a barcode is one of ~96 values;
a dataset name is one of a handful. Each got its own heap `String` per read. Python
explicitly converts these to pandas categoricals to avoid exactly this
(`nanoget/utils.py:15`).

Resolved by the columnar redesign rather than piecemeal, as recommended: `run_id`,
`barcode` and `dataset` are `DictColumn`s — a code per read into a dictionary of distinct
values — and `read_id` is a `StringColumn`, one buffer plus offsets rather than an
allocation per read.

### 22. Summary statistics computed once per file and then thrown away ✅

`src/extract.rs:93` → `src/metrics.rs:117`, then `src/extract.rs:58` → `src/metrics.rs:149`

`process_single_file` returns `MetricsCollection::new(reads)`, running the full
`MetricsSummary::from_reads` pass. `MetricsCollection::combine` then discards every one
of those summaries and recomputes over the concatenation. For an N-file run that is N+1
full statistics passes where 1 is needed, each allocating the vectors in finding 23.

### 23. Statistics allocate two full copies of the data per metric

`src/metrics.rs:359`, `:363`, `:371-374`, `:382-383` build four `Vec<f64>` of up to N
elements; `StatsSummary::from_values` then does `values.to_vec()` at `:457` for the sort.

For 20M aligned reads that is 160 MB per metric for the collect plus another 160 MB for
the sort copy, ×4 metrics — on top of the ~3.8 GB the `ReadMetrics` occupy. `mean` and
`std_dev` (`:462`, `:470`) are computed from the unsorted `values` while everything else
uses `sorted_values`, so both live simultaneously.

### 24. The entire output was materialized as one `String` before writing ✅

`src/main.rs:29-30`, `src/metrics.rs:232`

`to_tsv` builds one growing `String` for all reads with a fresh `format!` temporary per
read at `:232`. The JSON path calls `serde_json::to_string_pretty` on the whole
collection. Neither streams. Measured: for 2M reads that is ~370 MB (TSV) / ~680 MB
(JSON) of peak RSS on top of the records — paid even when the destination is a file.
`write!` into a `BufWriter` would make both O(1). `src/main.rs:36` also uses
`std::fs::write`, which requires the whole string by construction.

### 25. Every parser accumulator started at zero capacity ✅

`src/extract.rs:109`, `:152`, `:172`, `:323`, `:368`, `:417`; `src/metrics.rs:123`

`Vec::new()` then push-per-read means ~log₂(N) reallocation-and-memcpy rounds of
192-byte records; for 20M reads the final doubling alone copies ~3.8 GB. File size (or,
for `combine`, the sum of the input lengths at `src/metrics.rs:123`) gives a usable
capacity estimate.

## Public API surface

### 26. `MetricsCollection` lets `reads` and `summary` desynchronize

`src/metrics.rs:106-112`

Both fields are `pub`, and `summary` is only computed in `new`. Mutating `reads`
afterwards leaves `summary` stale with no indication — and the crate's own test does
exactly that (`tests/library_api_tests.rs:55-56` assigns `collection.reads[0].dataset`
after construction). nanoplotrs reads `metrics.reads` and moves out of it
(`nanoplotrs/src/lib.rs:125`), so it dodges the trap; nothing stops the next consumer
from trusting a `summary` that no longer describes `reads`.

### 27. `ExtractArgs` is a clap struct doing duty as the library's parameter object

`src/cli.rs:19-59`, used at `src/lib.rs:61-72` and `nanoplotrs/src/lib.rs:82-93`

**Partly addressed by the finding-13/14 work:** `file_type` is now `Option`, the three
stringly-typed fields are enums, and `convenience::extract_auto` covers the common case.
What remains is the shape of the struct itself.

`output` and `output_format` are read only by `main.rs` — `extract_metrics` ignores both
— yet every library caller must supply them. nanoplotrs dutifully passes
`output_format: "json"` and `output: None` for values that do nothing. There is no
`Default` impl and no `#[non_exhaustive]`, so all ten fields are mandatory at every
construction site and adding an eleventh is a source break for every consumer (the
`convenience` module at `src/lib.rs:60` exists mainly to paper over this). `threads` is
doubly overloaded: it means BGZF decompression threads inside `process_bam`
(`src/extract.rs:286`) while the rayon file-level parallelism at `src/extract.rs:53` uses
whatever ambient pool the caller installed.

### 28. `with_alignment` is four positional arguments with confusable types

`src/metrics.rs:76-88` — `(u32, Option<f64>, Option<u8>, Option<f64>)`

`aligned_quality` and `percent_identity` are both `Option<f64>` and both optional,
separated only by an `Option<u8>`. Swapping them compiles. The only in-tree caller
passes `None` for the second (`src/extract.rs:348-353`), so the mistake would be
invisible today.

### 29. Stringly-typed enumerations in a typed API — fixed with finding 14 ✅

`src/cli.rs:35` (`output_format`), `:43` (`read_type`), `:55` (`combine`)

Each has a small closed set of valid values, each matched with a catch-all `_` arm that
silently means "the default" (`src/main.rs:31`, `src/metrics.rs:141`) or a runtime error
deep in a loop (`src/extract.rs:427`). `FileType` is already a proper `ValueEnum`; these
three are not.

### 30. Errors are stringly-typed where consumers need to branch

`src/extract.rs:66-68` returns `ProcessingError("No reads found in input files")` — a
consumer wanting to distinguish "empty input" from a genuine failure has to match on the
message. nanoplotrs works around it by re-deriving emptiness itself
(`nanoplotrs/src/lib.rs:105`). A `NanogetError::NoReads` variant would cost nothing.
(Note: the finding-2 fix added a *second* site raising this same string, in the stdin
path, so there are now two.) Meanwhile **two** variants are now never constructed:
`UnsupportedFormat`, and `InvalidInput` since the finding-14 enums moved read-type
validation into clap. Both carry `#[allow(dead_code)]` because removing a variant from a
public error enum is itself a breaking change — worth doing in the same pass as any other
`NanogetError` change.

### 31. `#[allow(dead_code)]` scattered across genuinely-public API ✅

`src/metrics.rs:153`, `:162`, `:175`, `:187`, `:199`, `:212`, `:219`;
`src/formats.rs:37`, `:159`; `src/utils.rs:57`, `:72`

These are `pub` items re-exported from the library — including `FileType::sniff`, which
nanoplotrs is the primary consumer of. The attribute is silencing the *binary*'s
dead-code analysis (`src/main.rs:3-8` declares the modules a second time as a private
tree), i.e. the lint is suppressed on the public API for a reason unrelated to the public
API. It also means an item that really does become dead will never be noticed.

Fixed at the root rather than by removing attributes: `main.rs` now does
`use nanoget_rs::{...}` instead of re-declaring all six modules as a private tree, so the
binary links the library instead of compiling the crate a second time.

With that, **all 14 `#[allow(dead_code)]` attributes were deleted and nothing warns** —
confirming they were suppressing the duplicate compile and nothing else. The lint is
meaningful again: an item that really does become dead will now be reported.

### 32. JSON output was not reproducible between runs ✅

`src/metrics.rs` — `channel_distribution: Option<HashMap<u16, usize>>` and
`barcode_distribution: Option<HashMap<String, usize>>`

Found while byte-comparing output across the Tier 1 change: two runs of the *same* binary
on the same input produce different JSON, because `HashMap` iteration order is randomised
per process. The parsed content is identical — only the key order moves.

That makes the output undiffable, unhashable for provenance, and awkward to assert on in
tests. For a tool whose output goes into analysis records this is worth fixing, and the
fix is to swap both maps for `BTreeMap`, which also sorts channels numerically for free.
The types are public, so it is a (small) breaking change.

Fixed by switching both distributions to `BTreeMap`. Output is now byte-identical across
runs, and channels come out numerically sorted for free. Nothing outside the crate
consumed these maps, so the (technically breaking) type change cost nothing.

Regression test: `tests/fixture_tests.rs::test_json_output_is_deterministic`.

## The columnar redesign

The design question at the end of this review — whether a 192-byte row struct was the
right shape — was answered by rebuilding the storage. This section records what changed
and what it cost.

### What it is

`MetricsCollection::reads` is a `ReadColumns`: one array per field, in `src/columns.rs`.

- **A column an input never populates is never allocated.** A plain FASTQ sets 3 of the 13
  fields; the row layout paid for all 13 on every read. Columns are created lazily on the
  first present value and back-filled, so a field only some reads carry costs nothing
  until it appears.
- **Absence has two levels.** The whole column is `None` when the format has no such
  field; within a present column, a per-read absent value is marked in-band with a
  sentinel rather than a validity bitmap, because every field has a natural one — `NaN`
  for floats (which is already how the parsers treat an unmeasured value), 255 for
  `mapping_quality` (what SAM itself means by "unavailable"), 0 for `channel_id` (channels
  number from 1).
- **Strings are packed.** `read_id` is a `StringColumn` — one buffer plus `u32` offsets.
  `run_id`, `barcode` and `dataset` are `DictColumn`s — a code per read into a dictionary
  — since they repeat across every read of a file (finding 21).
- **`ReadMetrics` survives as the row type.** It is built transiently while parsing, handed
  to `ReadColumnsBuilder::push`, and never stored. `ReadView` borrows a read back out with
  the same fields as accessor methods, so row-wise code — a TSV line, a filter predicate —
  reads as it did.
- **Floats are `f32`.** Ample for a Phred score or a percent identity, half the width.
- **The wire format is unchanged.** A hand-written `Serialize` emits the same
  `{"reads": [...], "summary": {...}}` JSON, materialising one row at a time.

### What it cost and bought

Measured on a release build, 2M x 300 bp reads and a 4M-row summary:

| | before | after | |
| --- | --- | --- | --- |
| `fastq-minimal`, TSV | 1.08 s / 411 MB | 0.96 s / **44 MB** | 9.3x |
| `fastq`, TSV | 1.58 s / 491 MB | 1.92 s / **98 MB** | 5.0x |
| `fastq-rich`, TSV | 2.01 s / 554 MB | 2.10-2.39 s / **126 MB** | 4.4x |
| summary, 4M rows | 3.16 s / 865 MB | 3.13-3.30 s / **201 MB** | 4.3x |

Run time is unchanged within run-to-run noise: the builder does more branching per read
but writes far less memory, and the two cancel.

**The one visible cost is `f32` precision.** On the nanotest alignment, 3 of 960 reads
shift percent identity by 0.001 percentage points — one ulp at the printed precision —
and read qualities move by under 1e-6 Phred. Summary means agree to nine significant
figures. Documented in the README and CHANGELOG.

### Impact on nanoplotrs

249 insertions, 166 deletions across five files. **Its `NanoStats.tsv` is byte-identical**
before and after, and it produces the same plots.

- `stats.rs` **got simpler**, as predicted: four full-length `Vec` copies became borrowed
  columns.
- `filter.rs` was rewritten around indices — filter to a `Vec<usize>`, then gather once.
  `clip_to_percentile_for_plots` returns `Option` so a no-op does not copy — though with
  the default `--percentile 99` the common case does clip, and does copy.
- `plots/time_plots.rs` was the bulk of it, as expected, but easier than feared:
  `ReadView` is `Copy` and borrowing, so it dropped straight into the seven signatures
  that took `&ReadMetrics`, and the column-selector closures kept their shape.
- `lib.rs` no longer scans every read to decide which plots to draw — `has_quality()`,
  `has_time()` and `has_alignment()` are properties of the layout.

**The bottleneck moved.** Extraction of a 2M-read FASTQ now peaks at 175 MB, while
nanoplotrs as a whole peaks at 477 MB — so roughly 300 MB is now nanoplotrs' own plotting
buffers (`lengths`, `log_lengths`, the scatter pairs, the density grids), not the metrics.
That is where to look next if memory matters again; `--downsample` already cuts it to
193 MB.

### Reviewed independently

A fresh subagent reviewed the redesign. Its randomized differential test — 2000 trials of
random parts with random per-field presence, through the builder, `combine` in both modes
and `select` with duplicate indices, compared field-by-field against a shadow
`Vec<ReadMetrics>` — found no mismatches, and confirmed every allocated column is exactly
`len` long. It did find real defects, since fixed:

- **JSON printed 16-17 digits of an `f32`**, diverging from the previous `f64` pipeline at
  the *eighth* significant figure rather than the last, as the CHANGELOG had claimed. Rows
  now serialise as `f32`, so the output carries the precision that exists.
- **`MetricsCollection::summary` was recomputed by every `select`** and never read by the
  only consumer — 64% of `select`'s cost at 2M reads. It is now a lazily-computed method,
  which also closes finding 26: it can no longer desynchronise from the reads.
- **`channel_id` 0 was the absent marker** and is a real value in summary files. The
  sentinel is now `u16::MAX`.
- **`StringColumn` offsets were `u32`** and wrapped silently past 4 GiB of packed ids
  (~119M UUIDs); now `u64`.
- **A blank `barcode_arrangement` became a literal `""` barcode** — the one summary field
  not routed through `optional_field`.
- **`DictColumn::fill` invented a dictionary entry for an empty part**, so a tracked
  dataset with no reads was still listed by `dataset_names()`.
- **`select` silently skipped out-of-range indices**; now `debug_assert`ed and documented.
- Documentation corrections: the `f32` claim above, a stale CHANGELOG line about
  `combine`'s signature, "one allocation for all ids" (the arena grows by doubling; it now
  at least reserves up front), and the claim that the `clip_to_percentile` no-op path is
  the common one.
- In nanoplotrs: `total_aligned_bases` had changed meaning for the all-zero case, and the
  comment justifying the `downsample` sort was wrong — the time plots sort by start time
  themselves.

`src/columns.rs` had **no tests at all**, which is how those defects survived. It now has
14, covering late-appearing columns, heterogeneous `concat`, `select` with duplicates and
out-of-range indices, empty-vs-absent ids, dictionary reuse and replacement, sentinel
round-trips and nanosecond timestamps.

### Left undone

- **`read_id` is still always stored** — 76 MB of the 175 MB extraction peak at 2M reads,
  for a field nanoplotrs uses only under `--raw`. Making it opt-in is the single largest
  remaining item and needs only a flag on `ExtractArgs`.
- `DictColumn::push` does a linear scan over distinct values. Correct and fast for the
  handful of run ids or ~96 barcodes it is designed for; it would degrade on a column with
  thousands of distinct values, which none of the current ones are.

---

## On the design

The original closing note argued that the row-oriented `ReadMetrics` was the wrong shape,
and that a columnar layout would cut memory by roughly an order of magnitude. That has now
been done and measured: 4-9x depending on input, at no run-time cost, with nanoplotrs
migrated in the same pass and its output unchanged. The prediction that nanoplotrs would
be *easier* to write against columns held — it was already converting rows to columns at
every use site, so the row struct had been a translation layer serving code that never
wanted rows.

What remains genuinely open is smaller and listed above: `read_id` should be opt-in, and
nanoplotrs' own plotting buffers are now the larger term. Neither is a design question.
